# 1. Назначение документа

Настоящий `Task.md` определяет требования к дальнейшему развитию существующего приложения — генератора игровых ников.

Документ является основным рабочим заданием для агента-разработчика.

Агент обязан:

1. сначала изучить существующую реализацию;
2. сопоставить текущий код с требованиями настоящего документа;
3. сохранить работоспособные части существующего генератора;
4. не переписывать приложение без необходимости;
5. реализовывать систему поэтапно;
6. не принимать самостоятельно продуктовые решения, которые в настоящем документе обозначены как неутверждённые.

Главная задача — превратить существующий генератор в полноценное приложение для создания игровых ников с быстрым и персонализированным режимами, отдельным режимом невидимых ников, двумя языками интерфейса и возможностью дальнейшей монетизации.

- превращать модель в каталог конкретных игр;
- добавлять зависимость ядра генератора от конкретных игр.

# 3. Основная концепция продукта

Приложение предназначено прежде всего для геймеров.

Главный принцип:

> Для генерации персонального игрового ника не требуется база конкретных игр.

Вместо выбора игры пользователь описывает нужный ему ник через набор стандартных игровых параметров и при необходимости дополняет их собственными английскими словами.

Это позволяет использовать приложение:

- для существующих игр;
- для новых игр;
- для малоизвестных игр;
- для игр, отсутствующих в каком-либо каталоге;
- для игровых платформ;
- для Discord, Steam и других игровых сообществ.

Приложение не должно зависеть от постоянно обновляемого списка конкретных игр.

# 4. Основные режимы

В MVP должны существовать три самостоятельных режима.

```text
GAMER NICKNAME GENERATOR

1. QUICK NICKNAME
   Быстрый ник

2. CUSTOM NICKNAME
   Персональный ник

3. INVISIBLE NICKNAME
   Невидимый ник
```

Механизмы этих режимов различаются и не должны быть реализованы как один набор случайных настроек.

---

# 5. Режим 1 — Quick Nickname / Быстрый ник

## 5.1. Назначение

Режим предназначен для пользователя, который хочет максимально быстро получить игровые ники и не хочет заполнять параметры.

Основной сценарий:

```text
Открыть приложение
        ↓
Быстрый ник
        ↓
Сгенерировать
        ↓
Получить набор вариантов
```

Пользователь должен иметь возможность получить результат практически одним действием.

## 5.2. Дополнительные настройки

Допускается предоставить несколько необязательных настроек, например:

- Nick Style;
- Length;
- Numbers;
- Symbols.

Однако отсутствие выбора не должно блокировать генерацию.

## 5.3. Основной принцип

Все параметры имеют разумные значения по умолчанию.

Кнопка `Generate` должна работать даже без предварительного заполнения каких-либо полей.

---

# 6. Режим 2 — Custom Nickname / Персональный ник

Это основной интеллектуальный режим продукта.

Пользователь создаёт смысловой профиль будущего ника через стандартный набор параметров.

После стандартного выбора пользователь может добавить собственные параметры.

Нормативный состав параметров определяется обязательным приложением:

**[SEMANTIC_GAME_PARAMETER_BASE.md](./SEMANTIC_GAME_PARAMETER_BASE.md)**

---

# 7. Стандартная модель параметров

Стандартные параметры должны быть представлены в виде структурированной модели.

Минимальные категории:

```text
genre
setting
role
play_style
nick_style
length
structure_preferences
custom_words
```

Подробный нормативный состав значений, семантических тегов и связей задаётся в `SEMANTIC_GAME_PARAMETER_BASE.md`.

Ни один стандартный параметр, кроме технически необходимых ограничений результата, не должен быть обязательным для пользователя.

---

# 8. Каноническая модель параметров

Все внутренние идентификаторы параметров должны храниться на английском языке.

Пример:

```text
genre = rpg
setting = dark_fantasy
role = necromancer
play_style = strategic
nick_style = mysterious
length = short
```

Русские строки интерфейса не должны становиться внутренними значениями бизнес-логики.

Запрещено создавать две независимые модели параметров — русскую и английскую.

Должна существовать одна каноническая английская модель.

---

# 9. Пользовательские дополнительные параметры

После стандартного выбора пользователь получает возможность добавить собственные параметры.

Пример:

```text
dragon
frost
moon
wolf
shadow
Alex
77
```

Допускаются короткие английские фразы, например:

```text
ancient dragon
ice mage
black wolf
```

---

# 10. Язык пользовательских параметров

Принято обязательное продуктовое правило:

> Все параметры, которые пользователь вводит вручную для генерации ника, вводятся только на английском языке.

Это правило действует независимо от выбранного языка интерфейса.

Пример для русской версии:

```text
Дополнительные слова

Введите слова на английском:

dragon, frost, wolf
```

Пример для английской версии:

```text
Additional words

Enter words in English:

dragon, frost, wolf
```

---

# 11. Проверка пользовательского ввода

Поле пользовательских параметров должно:

1. принимать латинские буквы;
2. принимать цифры;
3. принимать допустимые разделители;
4. поддерживать несколько слов;
5. поддерживать короткие английские фразы;
6. не требовать от пользователя знания внутренней терминологии приложения.

При вводе кириллицы приложение должно корректно сообщать, что пользовательские параметры необходимо вводить на английском языке.

В MVP запрещено без отдельного решения:

- автоматически переводить русский текст;
- автоматически транслитерировать русский текст;
- обращаться к внешнему LLM только ради понимания обычных параметров.

---

# 12. Интерпретация дополнительных параметров

В MVP не требуется использовать LLM для интерпретации пользовательских параметров.

Применяется детерминированная модель:

```text
User Input
    ↓
Normalizer
    ↓
Known Terms / Unknown Terms
    ↓
Semantic Profile
    ↓
Nickname Generator
```

## 12.1. Известные слова

Если слово присутствует в словаре или известно через синоним, система может привести его к общей смысловой категории.

## 12.2. Неизвестные слова

Неизвестное английское слово не должно удаляться.

Пример:

```text
Zerathium
```

Если система не знает его смысла:

```text
custom_keyword = Zerathium
```

Слово может использоваться непосредственно как материал генерации.

## 12.3. Запрещённое поведение

Генератор не должен:

- отбрасывать неизвестные пользовательские слова без причины;
- придумывать им несуществующее значение;
- требовать обязательного распознавания каждого слова;
- обращаться к LLM при каждом запросе;
- зависеть от внешнего AI API для базовой генерации.

# 13. Semantic Profile

Необходимо сформировать центральную внутреннюю структуру `SemanticProfile`.

Пример:

```text
genre = rpg
setting = dark_fantasy
role = necromancer
play_style = strategic
nick_style = mysterious
length = short

themes:
  dragon
  frost

custom_keywords:
  Vornek
```

`SemanticProfile` должен стать стандартным входом для персонального генератора.

Конкретный интерфейс класса/структуры определяется исходя из технологии существующего приложения.

Нормативная семантика полей определяется `SEMANTIC_GAME_PARAMETER_BASE.md`.

---

# 14. Семантическая база

Необходимо использовать отдельную базу параметров генерации.

Это не база конкретных игр.

Логическая структура включает:

```text
genres
settings
roles
play_styles
nickname_styles
themes
semantic_tags
synonyms
semantic_groups
word_patterns
generation_rules
```

Полный стартовый набор определяется в:

**[SEMANTIC_GAME_PARAMETER_BASE.md](./SEMANTIC_GAME_PARAMETER_BASE.md)**

# 15. Ответственность за предметную модель

Агент-разработчик не должен самостоятельно придумывать предметную модель продукта.

Агент:

- реализует утверждённую модель;
- проверяет её техническую непротиворечивость;
- может выявлять проблемы;
- может предлагать дополнения;
- не меняет утверждённую модель самостоятельно.

Изменение нормативной семантической модели требует отдельного продуктового решения.

---

# 16. Генератор

Генератор должен использовать комбинацию:

```text
standard parameters
+
semantic tags
+
custom keywords
+
generation rules
```

Результаты не должны сводиться к простому случайному соединению двух слов.

Необходимо предусмотреть несколько способов формирования ника, включая:

```text
word combination
word shortening
phonetic modification
prefix
suffix
controlled letter replacement
semantic combination
custom keyword mutation
compact form
multi-word form
```

Генератор должен уметь создавать несколько существенно отличающихся вариантов за одну генерацию.

---

# 17. Разнообразие результатов

При одной генерации пользователь не должен получать набор почти одинаковых вариантов:

```text
DarkWolf1
DarkWolf2
DarkWolf3
DarkWolf4
```

Результаты должны различаться по механизму построения.

---

# 18. Повторная генерация

Должна существовать функция `Generate more`.

При повторной генерации система должна учитывать предыдущие результаты текущей сессии и по возможности не выдавать те же ники повторно.

---

# 19. Проверка результата

Перед показом ника должен выполняться validator.

Минимально проверяются:

- допустимая длина;
- допустимые символы;
- отсутствие пустого значения;
- отсутствие явного технического мусора;
- отсутствие запрещённых комбинаций из локального фильтра;
- отсутствие дублирования внутри текущей выдачи.

Фильтр запрещённой лексики должен быть отделён от основного генератора и допускать расширение.

---

# 20. Режим 3 — Invisible Nickname / Невидимый ник

`Invisible Nickname` является самостоятельным режимом.

Он не использует Semantic Profile обычного генератора.

Основной сценарий:

```text
Invisible Nickname
        ↓
Выбрать вариант
        ↓
Generate
        ↓
Copy
```

---

# 21. Типы невидимого ника

На первом этапе предусмотреть архитектурную возможность нескольких типов:

```text
fully_invisible
almost_invisible
spaced
```

Конкретный стартовый набор символов должен быть проверен технически.

Не считать любой Unicode-символ универсально поддерживаемым.

---

# 22. Совместимость невидимых ников

Разные игры и платформы могут:

- разрешать разные символы;
- удалять невидимые символы;
- нормализовывать Unicode;
- запрещать пустые или визуально пустые значения.

Поэтому приложение не должно обещать универсальную совместимость.

В интерфейсе должна присутствовать оговорка:

```text
Compatibility depends on the game or platform.
```

RU:

```text
Совместимость зависит от игры или платформы.
```

В будущем допускаются compatibility profiles:

```text
generic
steam
discord
other
```

Создание базы конкретных игр для невидимых ников не является обязательным требованием MVP.

Создание двух независимых приложений запрещено.

# 36. База конкретных игр

Для MVP каталог из 20 конкретных игр **не требуется**.

20 выбранных игровых экосистем используются только как источник для формирования универсальной семантической базы в `SEMANTIC_GAME_PARAMETER_BASE.md`.

Основной механизм должен работать без знания названия игры.

Это принципиальное архитектурное решение.

---

# 37. Возможность будущих игровых пресетов

Архитектура должна позволять в будущем добавить готовые пресеты конкретных игр.

Но пресет конкретной игры должен быть всего лишь заранее подготовленной комбинацией стандартных параметров.

Ядро генератора не должно зависеть от существования этого пресета.

# 40. Принцип минимального трения

Чем меньше информации пользователь хочет вводить, тем меньше приложение должно требовать.

Необходимо поддерживать:

```text
минимальный ввод → допустимый результат
подробный ввод → более персонализированный результат
```

Нельзя превращать генерацию в длинную обязательную анкету.

- потенциально переиспользуемые компоненты;
- проблемные места.

CURRENT_STATE_REPORT.md

# 43. Этапы реализации

3. Создание `SemanticProfile`.
4. Техническая реализация стартовой semantic database.
5. Интеграция semantic model с существующим генератором.
6. Реализация Quick Nickname.
7. Реализация Custom Nickname.
8. Поддержка custom English parameters.
9. Реализация Invisible Nickname.
10. RU/EN localization.
11. Централизованная инфраструктура FREE/PRO.
12. Firebase Analytics.
13. Тестирование.
14. Release readiness audit.

# 44. Требования к тестам

Тестирование должно включать как минимум:

### Quick generation

- генерация без параметров;
- генерация с дополнительными настройками;
- отсутствие пустого результата.

### Custom generation

- один параметр;
- несколько параметров;
- полный профиль;
- неизвестные custom words;
- смешанный набор известных и неизвестных слов;
- повторная генерация;
- отсутствие повторов в одной выдаче.

### Input validation

- English words;
- digits;
- allowed separators;
- Cyrillic input;
- пустой ввод;
- очень длинный ввод;
- специальные символы.

### Localization

- EN;
- RU;
- переключение языка;
- сохранение языка;
- отсутствие попадания русских UI-значений во внутреннюю semantic model.

### Invisible nickname

- генерация;
- копирование;
- отсутствие технически пустого результата;
- отображение предупреждения о совместимости.

### Analytics

- корректное событие;
- корректные параметры события;
- отсутствие передачи самого ника;
- отсутствие передачи raw custom words.

# 45. Критерии готовности MVP

MVP считается функционально готовым, когда:

1. приложение запускается стабильно;
2. пользователь может выбрать RU или EN;
3. Quick Nickname работает без заполнения параметров;
4. Custom Nickname работает со стандартными параметрами;
5. пользователь может добавлять собственные английские параметры;
6. кириллический custom input корректно отклоняется или сопровождается понятным сообщением;
7. неизвестные английские слова не теряются;
8. Semantic Profile корректно формируется;
9. генератор создаёт разнообразные варианты;
10. существует повторная генерация;
11. ник можно скопировать;
12. Invisible Nickname работает как отдельный режим;
13. интерфейс не зависит от списка конкретных игр;
14. RU/EN используют одну бизнес-логику;
15. аналитические события работают;
16. raw custom words не передаются в аналитику;
17. архитектура допускает FREE/PRO;
18. существующая рабочая функциональность не сломана;
19. тесты проходят;
20. агент подготовил итоговый отчёт;
21. техническая реализация соответствует обязательному приложению `SEMANTIC_GAME_PARAMETER_BASE.md`.

---

# 46. Что не входит в MVP

Если отдельно не утверждено, не реализовывать:

- базу сотен или тысяч игр;
- обязательный каталог конкретных игр;
- AI/LLM-интерпретацию свободного текста;
- автоматический перевод пользовательского текста;
- автоматическую транслитерацию;
- социальную сеть;
- чат;
- рейтинг игроков;
- пользовательские публичные профили;
- облачную синхронизацию;
- собственную серверную аналитику;
- собственную платёжную систему;
- web-версию;
- генерацию аватаров;
- проверку доступности ника во всех игровых сервисах;
- массовое использование внешних API.

# 50. Ограничение полномочий агента

Агент не имеет права самостоятельно изменять следующие продуктовые решения:

1. три основных режима;
2. отсутствие обязательной базы конкретных игр;
3. английский язык ручного ввода параметров;
4. RU/EN интерфейс;
5. единая английская внутренняя semantic model;
6. отсутствие обязательного LLM в MVP;
7. отдельный механизм Invisible Nickname;
8. необходимость аналитики;
9. запрет передачи raw custom words в аналитику;
10. отсутствие собственной платёжной системы;
11. принцип сохранения существующей рабочей реализации;
12. нормативную предметную модель обязательного приложения `SEMANTIC_GAME_PARAMETER_BASE.md`.

Если агент обнаруживает техническое противоречие, он обязан:

```text
описать проблему
→ показать место в коде
→ объяснить последствия
→ предложить вариант решения
```

и не менять утверждённое продуктовое решение молча.

# 52. Итоговая цель

Получить расширяемый Gamer Nickname Generator, в котором пользователь может:

```text
открыть приложение
       ↓
выбрать RU / EN
       ↓
выбрать способ генерации

QUICK
CUSTOM
INVISIBLE
       ↓
получить несколько игровых ников
       ↓
выбрать / скопировать результат
```

При персональной генерации приложение должно работать по модели:

```text
стандартные параметры
+
английские пользовательские параметры
+
semantic database
+
generation rules
=
персональный игровой ник
```

Ключевой принцип продукта:

> Пользователь описывает нужный ему игровой образ, а не обязан искать свою игру в заранее подготовленном каталоге.

# 53. Нормативный комплект

Утверждённый комплект состоит из двух файлов:

1. `Task.md`
2. `SEMANTIC_GAME_PARAMETER_BASE.md`

Оба файла обязательны для работы агента.

`Task.md` определяет, **что требуется реализовать**.

`SEMANTIC_GAME_PARAMETER_BASE.md` определяет, **на какой утверждённой предметной и семантической модели должна строиться реализация**.

Работа только по одному из этих файлов считается неполной.
